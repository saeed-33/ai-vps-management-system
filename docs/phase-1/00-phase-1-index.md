# المرحلة الأولى: تثبيت النطاق والبنية

هذه المرحلة هدفها تحويل فكرة النظام إلى مواصفات قابلة للتنفيذ قبل كتابة الكود التشغيلي.

## المخرجات

- `architecture.md`: البنية النهائية المقترحة ومسؤوليات كل طبقة.
- `model-strategy.md`: قرار استخدام النماذج الذكية في تحليل تقارير المراقبة.
- `permissions-model.md`: نموذج الصلاحيات للمستخدمين والوكيل والتنفيذ.
- `monitoring-profiles.md`: مفهوم ملفات المراقبة وصيغتها المقترحة.
- `specialist-agents.md`: تعريف الوكلاء المتخصصين وإدارتهم من لوحة الإدارة.
- `allowed-tools-and-solutions.md`: قواعد الأدوات والحلول المسموحة.
- `agent-workflow.md`: سير عمل الوكيل من المراقبة الدورية إلى عرض الحل على المستخدم.
- `mcp-contract.md`: عقد الربط بين لوحة الإدارة والوكيل عبر MCP.
- `deployment-plan.md`: تصور النشر الأولي والبيئات.

## قرارات أساسية

لا يوجد `RLHF` في المرحلة الحالية.

لا نبدأ بمودل متخصص لتقارير المراقبة. نبدأ ببنية تعتمد على:

- مودل عام قوي للتحليل والاستنتاج.
- مراقبة شاملة دورية لكل السيرفرات.
- وكيل فرعي لكل سيرفر أثناء دورة المراقبة.
- ملفات مراقبة سياقية وليست عتبات فقط.
- وكلاء متخصصون يتم تشغيلهم عند الحاجة.
- parsers ومقاييس حتمية قدر الإمكان.
- RAG من الوثائق والتقارير السابقة والحلول المعتمدة.
- مخرجات JSON قابلة للتحقق.
- نظام تقييم يقيس جودة التحليل قبل التفكير في التخصص.

## قاعدة الأمان الأساسية

```text
Default execution policy: deny all
```

الوكيل في النسخة الأولى يراقب، يحلل، يقترح، ويكتب تقارير. التنفيذ الفعلي على السيرفر الحقيقي ممنوع افتراضيا. الحل يمكن اختباره أو محاكاته في بيئة معزولة، ثم يعرض على المستخدم مع الأدلة والمخاطر ونتيجة الاختبار.
